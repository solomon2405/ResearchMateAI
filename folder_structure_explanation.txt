1. PROJECT OVERVIEW & TECHNOLOGY STACK
================================================================================
ResearchMate AI is a production-grade academic research platform built with
Django. It combines live scholarly discovery via the OpenAlex API with a
strictly grounded, multi-PDF Retrieval-Augmented Generation (RAG) assistant.

Core Technology Stack:
- Web Framework: Django 6.1 (Python 3.12+)
- Document Parser: PyMuPDF (fitz) for PDF text & metadata extraction
- Embeddings: Sentence-Transformers (all-MiniLM-L6-v2, 384-dimensional dense vectors)
- Vector Store: FAISS (Facebook AI Similarity Search - IndexFlatIP, Inner Product)
- Discovery Source: OpenAlex Works REST API with polite pool integration
- Synthesis Engine: Configurable LLM adapter (Deterministic Mock, Ollama, OpenAI-compatible)
- Database: SQLite (development) / PostgreSQL (production-ready ORM)

3. ROOT DIRECTORY FILES
================================================================================
.env
  Contains active local configuration and secret keys (DEBUG mode, SECRET_KEY,
  OpenAlex mailto email, LLM provider selection, FAISS vector index parameters).
  Must never be committed to public version control.

.env.example
  A safe, fully commented template illustrating all required and optional
  environment variables used across the application. Developers copy this to
  .env when bootstrapping a new environment.

.gitattributes
  Configures Git LFS (Large File Storage) tracking rules to manage large binary
  assets (such as *.mp4 presentation videos) outside standard Git commit blobs.

.gitignore
  Configures Git exclusions to prevent committing sensitive artifacts, including
  the SQLite database (db.sqlite3), uploaded private PDFs (media/private_documents/),
  compiled vector indexes (vector_indexes/), Python bytecode (__pycache__), and
  virtual environment directories (.venv/, venv/).

db.sqlite3
  The default local SQLite relational database file for development. It houses
  all relational tables (users, projects, documents, chunks, conversations,
  messages, and sources). In production, settings.py can switch to PostgreSQL.

FOLDER_STRUCTURE.txt & folder_structure_explanation.txt
  Comprehensive plain-text references explaining every directory, file, model,
  service, and data flow path across the ResearchMate AI codebase.

IMPLEMENTATION.md
  Detailed technical documentation describing the complete system architecture,
  relational schemas, algorithmic processing pipelines (PDF extraction,
  sliding-window chunking, vector indexing, similarity thresholding, citation
  grounding), security boundaries, and code inventory.

manage.py
  Standard Django CLI executable used for database migrations (makemigrations,
  migrate), starting the development server (runserver), executing test suites
  (test), and running administrative commands.

README.md
  Comprehensive project documentation providing the problem statement, system
  solution, feature list, architecture diagrams, installation instructions,
  configuration guide, and verification steps.

requirements.txt
  Specifies exact Python library dependencies:
  - Django >= 5.0 (core web framework)
  - pymupdf (PyMuPDF / fitz for fast, high-fidelity PDF extraction)
  - sentence-transformers (local dense vector embeddings)
  - faiss-cpu (vector similarity search engine)
  - httpx (asynchronous/synchronous HTTP client for OpenAlex API)
  - python-dotenv (environment variable loader)

ResearchMateAI.mp4
  Complete project demonstration and architecture walkthrough video for recruiters
  and evaluators. Showcases end-to-end user workflows, OpenAlex discovery,
  PyMuPDF document ingestion, isolated FAISS vector search, and evidence-grounded
  conversations with clickable citations. Tracked with Git LFS.

4. CORE CONFIGURATION (config/)
================================================================================
config/
  The primary Django configuration module that bootstraps the entire platform.

config/__init__.py
  Declares the directory as a Python package.

config/settings.py
  Centralized settings file. Key configurations include:
  - BASE_DIR: Resolves root repository paths.
  - INSTALLED_APPS: Registers Django contrib modules and the 5 custom apps:
    'accounts', 'research_projects', 'paper_discovery', 'documents', 'research_chat'.
  - MIDDLEWARE: Configures security, session, CSRF, and authentication layers.
  - TEMPLATES: Points to the root templates/ folder with app-level template discovery.
  - DATABASES: Configures SQLite database engine and file paths.
  - MEDIA_ROOT & PRIVATE_MEDIA_ROOT: Configures protected private document storage
    at media/private_documents/ to prevent direct unauthenticated downloads.
  - VECTOR_INDEX_DIR: Sets the storage directory for persistent FAISS index files.
  - RAG Configuration:
    * EMBEDDING_MODEL_NAME: 'all-MiniLM-L6-v2' (384-dimensional dense vectors)
    * VECTOR_STORE_BACKEND: 'faiss'
    * RAG_TOP_K: Maximum candidate passages to retrieve (default: 5)
    * RAG_SIMILARITY_THRESHOLD: Cosine similarity cutoff (default: 0.20)
    * RAG_MAX_CONTEXT_TOKENS: Context window budget (default: 3000 tokens)
    * LLM_PROVIDER: 'mock', 'ollama', or 'openai_compatible'
    * MAX_DOCUMENTS_PER_PROJECT: Maximum PDFs allowed per workspace (default: 30)
    * MAX_UPLOAD_SIZE_MB: Maximum PDF file size in MB (default: 25)

config/urls.py
  Master URL routing configuration that delegates URL prefixes to app routers:
  - '' -> research_projects.urls (dashboard and workspaces)
  - 'accounts/' -> accounts.urls (authentication)
  - 'discovery/' -> paper_discovery.urls (academic search)
  - 'documents/' -> documents.urls (PDF upload and streaming)
  - 'chat/' -> research_chat.urls (RAG chat interface and JSON APIs)

config/wsgi.py
  WSGI (Web Server Gateway Interface) entrypoint used for deploying synchronous
  production application servers such as Gunicorn or uWSGI.

config/asgi.py
  ASGI (Asynchronous Server Gateway Interface) entrypoint enabling async features
  and future WebSocket connections.

  - project_delete: Deletes a workspace along with cascading removal of attached

7. ACADEMIC LITERATURE DISCOVERY APP (paper_discovery/)
================================================================================
paper_discovery/
  Integrates with the OpenAlex API to search hundreds of millions of scholarly
  works, reconstruct inverted-index abstracts, and provide direct links to open-
  access PDFs and publisher DOIs.

paper_discovery/apps.py
  Defines PaperDiscoveryConfig (name = 'paper_discovery').

paper_discovery/models.py
  Provides foundations for bookmarked literature and saved search queries.

paper_discovery/forms.py
  - PaperSearchForm: Form containing fields for search query (keywords/title/DOI),
    minimum publication year, maximum publication year, and sorting criteria
    (relevance_score:desc, cited_by_count:desc, publication_date:desc).

paper_discovery/services/openalex.py
  - OpenAlexService:
    * search_works: Sends HTTP GET requests to the OpenAlex Works API.
    * Configures polite pool headers using OPENALEX_MAILTO for high reliability.
    * Maps parameters: query, publication year bounds, sorting, and pagination.
    * Handles HTTP timeouts, non-200 responses, and connection retries cleanly.

paper_discovery/services/normalizers.py
  - reconstruct_inverted_abstract: Converts OpenAlex's token-inverted index
    structures ({"Word": [pos1, pos2]}) into clean, continuous prose paragraphs.
  - normalize_openalex_work: Extracts and standardizes title, authors, publication
    year, journal/venue name, citation count, DOI URL, open-access status, and
    direct open-access PDF download links.

paper_discovery/views.py
  - search_view: Processes search input, invokes OpenAlexService, formats
    results with normalizers, handles pagination, and renders search.html.

paper_discovery/urls.py
  Maps routes:
  - /discovery/               [name='paper_search']

paper_discovery/tests.py
  Unit tests validating inverted index abstract reconstruction, OpenAlex API
  adapter error handling, polite pool header injection, and query sanitization.

8. PDF INGESTION & PRIVATE STORAGE APP (documents/)
================================================================================
documents/
  Handles uploading, security scanning, page-by-page text extraction, semantic
  sliding-window chunking, and ownership-gated serving of research PDFs.

documents/apps.py
  Defines DocumentsConfig (name = 'documents').

documents/models.py
  - ResearchDocument:
    * project: ForeignKey -> ResearchProject.
    * uploader: ForeignKey -> User.
    * original_filename: Name of the uploaded file.
    * file: FileField stored inside private_documents/%Y/%m/.
    * file_size: BigIntegerField tracking bytes.
    * checksum: CharField (SHA-256 hash) preventing duplicates in the same workspace.
    * detected_mime: Validated MIME type (e.g., 'application/pdf').
    * processing_status: State machine tracker ('uploaded', 'queued', 'extracting',
      'chunking', 'embedding', 'indexed', 'failed').
    * error_details: Diagnostic details if ingestion fails (e.g., scanned PDF alert).
    * total_pages: Total number of pages extracted.
  - DocumentChunk:
    * project: ForeignKey -> ResearchProject.
    * document: ForeignKey -> ResearchDocument.
    * chunk_index: Sequential integer position of chunk in the document.
    * page_start: 1-indexed page where passage begins.
    * page_end: 1-indexed page where passage ends.
    * text: Extracted passage text (~500-800 words).
    * vector_id: Integer position in the project's FAISS index.
    * embedding_model: Name of model used ('all-MiniLM-L6-v2').

documents/forms.py
  - DocumentUploadForm: Handles multi-file uploads. Validates PDF magic bytes
    (%PDF- header), MIME type, maximum file size (25MB), and workspace file limits (30 PDFs).

documents/services/pdf_extractor.py
  - extract_pdf_pages: Uses PyMuPDF (fitz) to open PDFs, iterate through pages,
    extract raw text, normalize whitespace, and count pages.
  - Scanned PDF Detection: Calculates text density per page. If text volume is
    insufficient, flags the document as scanned, alerting the researcher that
    OCR processing is required.

documents/services/chunker.py
  - chunk_document_pages: Implements an overlapping sliding-window chunking
    algorithm (~500-800 words per passage with ~100-word overlap). Meticulously
    tracks exact starting and ending pages for each chunk to support precision
    clickable citations.

documents/services/ingestion.py
  - process_and_index_document: Orchestrates the entire ingestion lifecycle:
    1. Update status to 'extracting'
    2. Extract text via extract_pdf_pages
    3. Verify text layer presence (abort if scanned)
    4. Chunk text via chunk_document_pages (status: 'chunking')
    5. Generate dense embeddings via embed_texts (status: 'embedding')
    6. Persist DocumentChunk records in the database
    7. Append embeddings into the project's FAISS vector store
    8. Update document status to 'indexed'

documents/views.py
  - upload_documents: Handles multi-file PDF POST requests, enforces SHA-256
    duplicate prevention, saves files, and triggers ingestion.
  - serve_private_document: Secured streaming endpoint (/documents/<id>/view/).
    Verifies user ownership before streaming PDF content with FileResponse.
    Blocks public direct URL access.
  - delete_document: Deletes document record, associated chunks, on-disk PDF,
    and updates vector index mappings.
  - retry_ingestion: Re-triggers ingestion pipeline for failed documents.

documents/urls.py
  Maps routes:
  - /documents/upload/<project_id>/     [name='upload_documents']
  - /documents/<doc_id>/view/           [name='serve_private_document']
  - /documents/<doc_id>/delete/         [name='delete_document']
  - /documents/<doc_id>/retry/          [name='retry_ingestion']

documents/tests.py
  Unit tests verifying PyMuPDF text extraction, chunk page tracking, scanned
  document flagging, SHA-256 duplicate rejection, and 403 Forbidden access guards.

9. RAG PIPELINE, VECTOR SEARCH & CHAT APP (research_chat/)
================================================================================
research_chat/
  Implements local dense vector search, project-isolated FAISS storage, strictly
  grounded LLM synthesis, citation validation, and conversational chat threads.

research_chat/apps.py
  Defines ResearchChatConfig (name = 'research_chat').

research_chat/models.py
  - ChatConversation:
    * project: ForeignKey -> ResearchProject.
    * owner: ForeignKey -> User.
    * title: CharField (thread title, e.g., "Biomarker Sensitivity Questions").
  - ChatMessage:
    * conversation: ForeignKey -> ChatConversation.
    * role: 'user' or 'assistant'.
    * content: Raw message text.
    * token_usage: JSONField tracking usage metrics.
    * processing_status: State tracker ('completed', 'failed').
  - MessageSource:
    * message: ForeignKey -> ChatMessage (links to assistant response).
    * document: ForeignKey -> ResearchDocument.
    * chunk: ForeignKey -> DocumentChunk (nullable on delete).
    * page_reference: String indicating page numbers (e.g., "p. 3-4").
    * excerpt: Passage snippet used as evidence.
    * similarity_score: Cosine similarity score between query and chunk.

research_chat/services/embeddings.py
  - LocalEmbeddingService: Singleton wrapper around sentence-transformers
    (all-MiniLM-L6-v2). Runs locally on CPU/GPU, producing normalized 384-d
    float32 vectors without external API calls or latency costs.

research_chat/services/vector_store.py
  - FAISSVectorStore: Manages project-specific FAISS IndexFlatIP (Inner Product)
    indexes stored at vector_indexes/project_<id>.index.
  - Maintains synchronized chunk ID mapping files (project_<id>_chunks.json).
  - Guarantees complete vector isolation: Project A can never query Project B.

research_chat/services/retriever.py
  - retrieve_project_evidence: Embeds user query, queries project FAISS index
    for top-k candidates, applies RAG_SIMILARITY_THRESHOLD cutoff, fetches
    corresponding DocumentChunk records, and formats evidence payloads.

research_chat/services/answer_generator.py
  - Configurable LLM synthesis adapter:
    * MockAnswerGenerator: Deterministic test engine producing grounded answers
      with [Source N] tags without external model dependencies.
    * OllamaAnswerGenerator: Connects to local Ollama instance (e.g., llama3.2).
    * OpenAICompatibleGenerator: Connects to OpenAI-compatible endpoints.
  - Strict Document Grounding Prompt: Explicitly instructs LLMs to answer
    strictly using provided evidence passages and state lack of evidence when
    queries cannot be substantiated.

research_chat/services/citation_validator.py
  - extract_and_validate_citations: Scans generated answers for [Source N] tags,
    cross-references them against retrieved project chunks, verifies document
    existence and page references, and produces structured citation records.

research_chat/services/rag_pipeline.py
  - execute_rag_query: Central RAG orchestrator:
    1. Authenticate user and verify conversation & project ownership.
    2. Persist user question as ChatMessage.
    3. Retrieve top-k evidence chunks via retrieve_project_evidence.
    4. Generate evidence-grounded answer via get_answer_generator.
    5. Validate citations via extract_and_validate_citations.
    6. Persist assistant answer and create MessageSource records.
    7. Return answer, citations, and evidence sufficiency status.

research_chat/views.py
  - chat_view: Renders conversational workspace with conversation sidebar.
  - create_conversation: Starts a new chat session within a project.
  - send_message_api: AJAX endpoint receiving user questions, invoking RAG
    pipeline, and returning JSON response with answer and citations.
  - rename_conversation: Allows renaming conversation thread titles.
  - delete_conversation: Deletes conversation thread and all messages.

research_chat/urls.py
  Maps routes:
  - /chat/<project_id>/                   [name='chat_view']
  - /chat/<project_id>/conversation/<id>/ [name='chat_view_conversation']
  - /chat/<project_id>/create/            [name='create_conversation']

13. PERSISTENT FAISS VECTOR INDEXES (vector_indexes/)
================================================================================
vector_indexes/
  Storage directory for local FAISS vector stores:
  - project_<id>.index: Serialized binary FAISS IndexFlatIP index containing
    normalized 384-dimensional dense vectors for all chunks in project <id>.
  - project_<id>_chunks.json: JSON mapping file binding FAISS vector positions

    ensuring zero cross-project vector leakage.

14. END-TO-END DATA FLOW PIPELINES
================================================================================

PIPELINE A: Academic Literature Discovery (OpenAlex)
  1. Researcher enters keyword, year range, and sorting preference in /discovery/.
  2. paper_discovery/views.py validates input via PaperSearchForm.
  3. paper_discovery/services/openalex.py sends GET request to api.openalex.org/works.
  4. paper_discovery/services/normalizers.py reconstructs inverted abstracts into
     readable text and parses author lists, DOIs, and direct PDF URLs.
  5. paper_discovery/templates/paper_discovery/search.html renders paper cards.
  6. Researcher reviews papers and downloads selected PDFs to local storage.

PIPELINE B: Document Ingestion & Vector Indexing
  1. Researcher uploads research PDFs via /documents/upload/<project_id>/.
  2. documents/views.py checks file size, MIME type, and computes SHA-256 checksum.
  3. ResearchDocument record is created with status 'extracting'.
  4. documents/services/pdf_extractor.py extracts text page-by-page using PyMuPDF.
  5. Scanned PDF detector verifies text density (flags OCR requirement if empty).
  6. documents/services/chunker.py generates overlapping passages (500-800 words),
     preserving page_start and page_end for every chunk.
  7. research_chat/services/embeddings.py generates 384-d normalized embeddings.
  8. DocumentChunk records are saved to the relational database.
  9. research_chat/services/vector_store.py appends vectors to project_<id>.index
     and writes project_<id>_chunks.json to disk.
  10. ResearchDocument status transitions to 'indexed'.

PIPELINE C: Evidence-Grounded RAG Chat
  1. Researcher sends a question in the chat interface (/chat/<project_id>/).
  2. static/js/chat.js dispatches POST request to send_message_api.
  3. research_chat/services/rag_pipeline.py validates project ownership.
  4. User's query is embedded into a 384-d vector via LocalEmbeddingService.
  5. FAISSVectorStore searches project_<id>.index for top-k nearest chunks.
  6. retriever.py filters out chunks with cosine similarity below threshold.
  7. answer_generator.py formats prompt with retrieved evidence and generates answer.
  8. citation_validator.py verifies [Source N] claims against actual project chunks.
  9. ChatMessage and MessageSource records are persisted in the database.
  10. Response is returned as JSON and rendered with clickable citation chips
      linking directly to the cited PDF pages.


================================================================================
15. MULTI-USER ISOLATION & SECURITY BOUNDARIES
================================================================================
ResearchMate AI enforces five distinct security boundaries:

1. Relational Database Boundary:
   Every query for workspaces, documents, chunks, and chat messages is scoped
   by request.user. Attempts to access objects belonging to other users trigger
   PermissionDenied (HTTP 403).

2. Private File Storage Boundary:
   Uploaded PDFs are stored outside the public document root. The only route to
   access a PDF is /documents/<id>/view/, which checks project ownership before
   streaming the file.

3. FAISS Vector Space Boundary:
   Each project owns an isolated FAISS index file (vector_indexes/project_<id>.index).
   Vector searches are strictly confined to the active project's file, preventing
   information leakage between workspaces.

4. Hallucination & Grounding Boundary:
   The synthesis prompt strictly confines the LLM to the retrieved evidence passages.
   If retrieved passages do not meet similarity thresholds, the system explicitly
   reports a lack of evidence rather than generating fabricated content.

5. Citation Verification Boundary:
   All citations generated by the assistant are validated against actual
   DocumentChunk IDs and page numbers in the active project. Unverifiable citations
   are discarded before display.
